# Отчёт по практической №1

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Радуль Неманя |
| Вариант (запрос) | Q16 |
| Масштаб sfN | sf10 |
| Почему выбран такой масштаб | Я выбрал sf10, потому что этого объёма достаточно, чтобы увидеть разницу между кодеками сжатия GZIP и ZSTD по размеру файлов и по времени записи. Если бы я взял меньший масштаб, например sf1, данных было бы слишком мало, поэтому всё считалось бы за секунды, и разницу между кодеками было бы трудно заметить и понять. Если бы я взял больший масштаб, таблицы создавались бы намного дольше и занимали бы много места на диске, а у меня сейчас и так осталось мало свободного места. Поэтому для меня sf10 является наилучшим выбором. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | MinIO работает как локальный аналог AWS S3, поэтому не нужен облачный аккаунт, а Trino и Spark подключаются к нему так же, как к обычному S3. Он поднимается одним контейнером, а данные лежат в томе и не пропадают после перезапуска. Кроме того, в нём есть веб-консоль, в которой удобно создавать бакеты и смотреть файлы. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Lakekeeper не умеет хранить информацию о таблицах сам по себе, поэтому ему нужна отдельная база, и он для этого использует PostgreSQL. Перед первым запуском каталога отдельной командой migrate в этой базе создаются таблицы самого каталога. База работает в отдельном контейнере, а её данные лежат в томе, поэтому каталог не теряет информацию о таблицах после перезапуска. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Trino сам не знает, какие файлы в MinIO относятся к какой таблице, поэтому ему нужен каталог. Lakekeeper как раз и есть такой каталог: он хранит информацию о таблицах, а Trino сначала спрашивает у него, где лежат данные, и только потом читает файлы. Выбран именно он, потому что это готовый REST-каталог для Iceberg, который запускается одним контейнером, а для работы ему нужен только PostgreSQL. Благодаря этому Trino и Spark видят одни и те же таблицы, и данные не нужно копировать. Другой вариант, Hive Metastore, тоже хранит информацию о таблицах, но он сложнее в установке и настройке. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Trino это SQL-движок: запросы пишутся на обычном SQL, а он сам спрашивает у Lakekeeper, где лежат данные, и читает или записывает файлы в MinIO. Для этой работы он подходит, потому что умеет работать с таблицами Iceberg. В нём есть встроенный коннектор tpch, который создаёт данные TPC-H прямо во время запроса, поэтому ничего скачивать не нужно. Кроме того, Trino быстро запускается и хорошо подходит для аналитических запросов, как мой запрос Q16. |
| (BI: Superset / Metabase) | отчёт/дашборд поверх Gold | BI-инструмент я не использовал, а вместо него выбрал Spark. Я познакомился с ним на лабораторной работе, когда заполнял таблицу с результатами и сравнивал время запросов в Trino и Spark. Поэтому мне было проще работать именно с ним. |

### Скрипты, которыми поднимал стек

Стек поднял по гайду, но с изменениями в портах. Стандартные порты PostgreSQL и Trino оказались заняты, поэтому запустил PostgreSQL на порту 5433, а Trino на порту 8081. Из-за этого в адресе базы для Lakekeeper указал порт 5433. Бакеты bronze, silver и gold создал в консоли MinIO, а три warehouse с такими же именами создал в интерфейсе Lakekeeper. Файлы каталогов Trino создал в папке catalog, по одному файлу на каждый слой и файл tpch.properties для генератора данных.  

```powershell
# MinIO: объектное хранилище, порт 9000 для S3 API, порт 9001 для веб-консоли, данные в томе minio-data
docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin -v minio-data:/data pgsty/silo:latest server /data --console-address ":9001"
# PostgreSQL: база для метаданных Lakekeeper, порт на компьютере 5433 вместо 5432, данные в томе pg-data
docker run -d --name lakehouse-pg -e POSTGRES_PASSWORD=postgres -p 5433:5432 -v pg-data:/var/lib/postgresql/data postgres:17
# Lakekeeper, миграция: создаёт таблицы каталога в PostgreSQL, запускается один раз
docker run --rm -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5433/postgres' -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5433/postgres' quay.io/lakekeeper/catalog:latest-main migrate
# Lakekeeper: Iceberg REST Catalog на порту 8181, адрес PostgreSQL указан с портом 5433
docker run -d --name lakekeeper -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5433/postgres' -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5433/postgres' -p 8181:8181 quay.io/lakekeeper/catalog:latest-main serve
# Trino: SQL-движок, порт на компьютере 8081 вместо 8080, папка catalog с файлами каталогов подключена в контейнер
docker run -d --name trino -p 8081:8080 -v "${PWD}\catalog:/etc/trino/catalog" trinodb/trino:476
```

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| part | partkey, brand, type, size | Колонка partkey нужна для соединения с partsupp. По колонкам brand, type и size идёт фильтр. Бренд не должен быть Brand#45, тип не должен начинаться с MEDIUM POLISHED, а размер должен входить в список из восьми значений. Эти же три колонки используются для группировки и выводятся в результате. |
| partsupp | partkey, suppkey | Колонка partkey нужна для соединения с part. По колонке suppkey исключаются поставщики с жалобами через NOT IN, а затем считается количество уникальных поставщиков через count DISTINCT. |
| supplier | suppkey, comment | В подзапросе по колонке comment находятся поставщики, у которых в комментарии есть жалобы клиентов. Их suppkey затем исключаются из partsupp. |

## 5. Тесты производительности

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | В первый раз, на холодном запуске, я получил 4,883 с, а в следующие два раза, на тёплом запуске, 1,919 с и 1,948 с. | 292,2 | Сжимает сильнее всего, и данные занимают на 26,6 МБ меньше, чем при ZSTD. Но запись заняла 31,7 с, то есть в полтора раза дольше. Запросы на тёплом запуске тоже оказались немного медленнее. |
| ZSTD | В первый раз, на холодном запуске, я получил 4,966 с, а в следующие два раза, на тёплом запуске, 1,697 с и 1,682 с. | 318,8 | Данные занимают примерно на 9 процентов больше, чем при GZIP, но запись заняла всего 21,1 с. На холодном запуске запрос выполнился почти так же, как при GZIP, а на тёплом немного быстрее. |

Для всех слоёв я выбрал ZSTD. Данные с GZIP занимают меньше места, но разница небольшая, всего около 27 МБ на весь слой Bronze. Запись с ZSTD прошла в полтора раза быстрее, за 21,1 с против 31,7 с. На холодном запуске запрос выполнился почти одинаково с обоими кодеками, а на тёплом запуске с ZSTD он оказался чуть быстрее. Хотя GZIP занимает меньше места, при записи он заметно медленнее, чем ZSTD. Поэтому для меня ZSTD оказался лучшим выбором.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Данных становится всё больше, и хранить их в обычной базе данных дорого и неудобно. В lakehouse данные лежат файлами в объектном хранилище, как в data lake, но работать с ними можно как с обычными таблицами через SQL, как в хранилище данных. Это хорошо было видно на лабораторных, где таблицы записывались в MinIO файлами parquet, а запросы к ним писались на обычном SQL через Trino. Ещё одно удобство в том, что данные и метаданные хранятся отдельно, поэтому одни и те же файлы могут читать разные движки, например Trino и Spark, и копировать данные для этого не нужно. Кроме того, слои медальона удалось разделить по отдельным бакетам, а сжатие помогло уменьшить размер данных. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В таблицу silver.lakehouse.parts_without_complaints добавил новую колонку source_note. У всех существующих строк в ней оказалось значение NULL, потому что старые файлы этой колонки не содержат. Затем переименовал колонку в check_note, и строки по-прежнему читаются с NULL. До изменений в таблице было 4 файла общим размером 27 281 488 байт, и после изменений число и размер файлов остались теми же. Значит, файлы не переписывались. Так получается потому, что Iceberg хранит колонки по ID, а не по имени, и все изменения записываются только в метаданные. |
| Пример скрипта восстановления данных из снапшота (time travel) | Сначала запомнил идентификатор текущего снапшота таблицы gold.lakehouse.q16_result. Затем удалил из неё все строки бренда Brand#11. Их было 1160, и в таблице осталось 26 680 строк. После этого прочитал старую версию таблицы через FOR VERSION AS OF, и в ней снова оказалось 27 840 строк, то есть удалённые данные никуда не пропали. В конце откатил таблицу к этому снапшоту командой rollback_to_snapshot, и строк опять стало 27 840. |

### Скрипт для примера schema evolution

```powershell
Шаг 1. Посмотреть количество и размер файлов до изменений.
SELECT count(*) AS files, sum(file_size_in_bytes) AS bytes
FROM silver.lakehouse."parts_without_complaints$files";

Шаг 2. Добавить новую колонку.
ALTER TABLE silver.lakehouse.parts_without_complaints ADD COLUMN source_note varchar;

Шаг 3. Проверить, что у старых строк в новой колонке NULL.
SELECT partkey, suppkey, source_note FROM silver.lakehouse.parts_without_complaints LIMIT 5;

Шаг 4. Переименовать колонку.
ALTER TABLE silver.lakehouse.parts_without_complaints RENAME COLUMN source_note TO check_note;

Шаг 5. Снова посмотреть количество и размер файлов.
SELECT count(*) AS files, sum(file_size_in_bytes) AS bytes
FROM silver.lakehouse."parts_without_complaints$files";
```

### Скрипт восстановления данных из снапшота

```powershell
Шаг 1. Узнать идентификатор текущего снапшота
SELECT committed_at, CAST(snapshot_id AS varchar) AS snapshot_id, operation
FROM gold.lakehouse."q16_result$snapshots"
ORDER BY committed_at;

Шаг2. Удалить строки бренда Brand#11
DELETE FROM gold.lakehouse.q16_result WHERE brand = 'Brand#11';

Шаг 3. Прочитать старую версию таблицы до удаления
SELECT count(*) FROM gold.lakehouse.q16_result FOR VERSION AS OF 7741756319158492962;

Шаг 4. Откатить таблицу к старому снапшоту
ALTER TABLE gold.lakehouse.q16_result EXECUTE rollback_to_snapshot(7741756319158492962);
```
